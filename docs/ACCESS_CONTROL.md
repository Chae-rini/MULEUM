# 회원과 접근 권한 설계

> 2026-10-23 추가 구현: SQL/RLS와 별도로 `/login`, `/member/[role]`, `/mypage`에 서버 인증·역할 검증 코드를 추가했다. 실제 Supabase는 미연결이며, 개발 모드의 가상 세션과 로컬 가상 Auth 서버로 검증했다. `/app`는 계속 독립된 학습 기능 시연이다. 연결 절차와 제한은 [개발 환경](DEVELOPMENT_SETUP.md)을 기준으로 한다.

## 현재 상태와 제한

회원 질문 기능의 추가 구현은 [QUESTION_FLOW.md](QUESTION_FLOW.md)를 따른다. `/member/questions`는 기존 인증, 담당 배정, 사용자 토큰과 새로운 SQL/RLS를 연결한다. 운영 Supabase는 아직 미연결이며 실제 정책 실행은 로컬 PostgreSQL과 가상 Auth 환경에서 검증한다. 아래 플랫폼 전체의 미완료 항목과 질문 기능의 완료 범위를 구분한다.

**현재 `/app`는 인증 없는 로컬 시연이다.** 역할 선택, 메뉴 숨김, 페이지 안내는 UI 구분이며 보안 장치가 아니다. 주소로 직접 접근하거나 같은 브라우저에서 역할을 바꾸면 가상 화면을 볼 수 있다. 브라우저 저장소에는 암호화되지 않은 기록이 남는다. 실제 학생 데이터를 사용하거나 실제 베타로 공개하지 않는다.

`robots: noindex`는 검색 노출 방지 안내일 뿐 접근 통제가 아니다. 현재 외부 계정, 인증 키, 데이터베이스, 파일 저장소를 연결하지 않았다.

## 독립적인 회원 속성

| 개념 | 설계 | 자동 추론하지 않는 것 |
| --- | --- | --- |
| 계정 | invited / active / suspended | 계정 존재가 가입 승인이라는 가정 |
| 역할 | 승인 상태를 가진 여러 RoleAssignment | 졸업 = 조교, 교사 = 관리자 |
| 연령 | minor / adult / unverified | 졸업 = 성인 |
| 재학 상태 | active / alumni / none | 졸업 = 모든 커뮤니티 접근 |
| 관계 | 주 담당 교사·추가 승인 교사·보호자 | 교사 역할 = 전체 학생 열람 |
| 공유 범위 | 목적·수신자·대상 기록·철회 상태 | 자료 저장 = 타인 공개 동의 |

`MemberProfile`, `RoleAssignment`, `StudentRelationship`은 `lib/platform.ts`의 타입 계약이다. 실제 세션이나 데이터베이스 정책은 아직 아니다. 한 회원의 역할 행은 여러 개일 수 있고 승인되지 않았거나 취소된 역할은 효력을 갖지 않는다.

## 권한 행렬 — 향후 서버에서 적용할 기준

| 자료 / 작업 | 학생 | 담당·추가 승인 교사 | 학부모 | 조교·졸업생 | 운영진·관리자 |
| --- | --- | --- | --- | --- | --- |
| 개인 물음 | 본인 관리 | 별도 공유된 항목만 | 별도 승인 리포트만 | 접근 없음 | 기본 접근 없음 |
| 개인 일기 | 본인만 조회·수정·삭제 | 접근 없음 | 접근 없음 | 접근 없음 | 역할만으로 접근 불가 |
| 수업 기록 | 본인에게 공유된 기록 | 승인된 관계와 범위 내 | 승인된 발췌 리포트 | 접근 없음 | 업무별 명시 권한만 |
| 교사 메모 | 자동 공개하지 않음 | 담당 관계·메모 정책에 따름 | 접근 없음 | 접근 없음 | 기본 접근 없음 |
| 학부모 리포트 | 본인의 공유 내용 확인 | 담당 교사의 작성·승인 범위 | 연결된 보호자 + 학생 동의 + 승인된 리포트 | 접근 없음 | 기본 접근 없음 |
| 게시판 | 허용 공간에서 작성 | 담당 또는 허용 공간에서 답변 | 별도로 허용된 자료만 | 승인 역할과 해당 공간 범위에서만 답변 | 담당 조정 업무 범위만 |
| 교육팀 연구 | 접근 없음 | 허용된 팀 문서 | 접근 없음 | 별도 허용 없으면 접근 없음 | 업무별 범위만 |
| 모임 | 연령·가입·활동 정책 적용 | 동일 | 동일 | 동일 | 운영 범위만, 연령 정책 유지 |
| 초대·역할 승인 | 없음 | 별도 위임 시만 | 없음 | 없음 | 해당 승인 권한을 가진 담당자만 |

이 표는 실제 권한 구현을 대신하지 않는다. 모호한 경우 기본 거부한다. 플랫폼 관리 기능과 개인정보 원문 열람은 다른 권한으로 유지한다. 인프라 관리자의 데이터베이스 접근도 최소화·감사하며, 애플리케이션의 역할 정책만으로 인프라 권한까지 차단됐다고 주장하지 않는다.

## 서버와 데이터베이스의 이중 검증 계획

1. 서버에서 인증된 세션을 확인한다. 브라우저의 역할 선택이나 전달된 `userId`를 신뢰하지 않는다.
2. 승인 역할, 계정 상태, 유효한 관계, 자료 공개 범위, 동의·철회 여부를 확인한다.
3. 데이터베이스 행 수준 보안 (Row Level Security, RLS)으로 각 행의 조회·입력·수정·삭제를 다시 제한한다.
4. 일기는 작성자 식별값과 인증된 본인 일치를 필수로 하며 관리자 역할 예외를 두지 않는다.
5. API, 서버 액션, 직접 REST 요청, 파일 다운로드 경로 모두 같은 권한을 검증한다. 레이아웃 검사만으로 충분하지 않다.
6. 승인된 리포트를 별도 데이터로 저장한다. 학부모 조회가 개인 일기·교사 메모를 조인하지 않게 한다.
7. 파일은 비공개 버킷과 소유·관계 정책을 사용한다. 공개 URL이나 만료 없는 공유 링크를 기본으로 사용하지 않는다.

서비스 역할 키는 클라이언트와 `NEXT_PUBLIC_` 환경 변수에 넣지 않는다. 사용자 요청마다 RLS를 우회하는 공용 관리자 클라이언트를 사용하지 않는다. 필요한 서버 관리 작업만 별도 권한·감사 아래 수행한다.

## 초대·승인·철회

초대에는 대상, 허용 역할, 만료, 단일 사용 여부, 발행자를 둔다. 초대 수락과 역할 승인은 같은 의미가 아니다. 민감한 역할은 별도 승인 상태를 확인한다. 교사 관계·보호자 관계·공유 동의 철회가 접근에 반영되는 경로를 검증한다.

### 2026-10-24 결정: 초대 링크 + Google 계정, 별도 회원가입 없음

구현: `supabase/migrations/202610240001_invitations_onboarding.sql`, `/member/invitations`(관리자), `/invite/[token]`, `/auth/google`, `/auth/callback`, `/welcome`.

| 단계 | 규칙 |
|---|---|
| 초대 만들기 | 관리자만. 구글 이메일 1개·역할 1개(학생·학부모·선생님·관리자)·만료 1~14일. 학생은 활성 담당 선생님 필수. 같은 이메일에 다시 만들면 이전 링크는 취소. 토큰 원문은 한 번만 화면에 표시하고 DB에는 SHA-256만 저장 |
| 초대 수락 | Google 로그인만 허용. 토큰의 이메일이 초대 이메일과 같아야 함. 만료·취소·사용된 링크와 이미 회원인 계정은 거절. 수락하면 계정은 `invited`, 역할은 `pending` — 아직 아무 화면도 열 수 없음 |
| 첫 로그인 확인 | 이름·생년월일·시군구·개인정보 수집·이용 동의. 만 15세 미만 거절. 만 19세 이상은 즉시 활성화(역할 승인, 학생이면 담당 선생님 배정) |
| 보호자 동의 | 만 19세 미만은 "동의 대기". 관리자가 보호자 확인 방법·날짜를 기록해야 활성화. 그 시점에 담당 선생님이 비활성이면 활성화 전체를 취소 |

초대받지 않은 구글 계정도 Supabase `auth.users`에는 생길 수 있지만, 회원 기록이 없으므로 세션을 즉시 폐기하고 어떤 화면도 열 수 없다.

프로필 직접 수정은 이름·시군구 열만 허용한다(`202610250001_profile_column_grants.sql`, 2026-10-24 결정). 생년월일은 연령·보호자 동의 판단의 근거라 회원이 바꿀 수 없고, 프로필 생성은 `complete_onboarding`만 한다. 성별(`member_optional_profiles`)은 권한·연령 판단에 쓰지 않으므로 본인 행 쓰기를 유지한다.

미정: 보호자 동의 문구·증빙 보존 기간, 구글 계정이 없는 학생의 예외 경로, 신고 처리, 자료 삭제·보관, 긴급 대응 절차. 운영·보호 정책을 확정하지 않고 실제 개인정보 수집을 시작하지 않는다.

## 보안 검증 완료 조건

- 비로그인 요청의 `/app` 실제 자료·API·파일 접근 거부.
- 학생 A가 학생 B의 ID로 요청해도 조회·수정·삭제 불가.
- 관계 없는 교사, 승인 취소된 교사, 무관한 보호자의 접근 거부.
- 학생 동의와 교사 승인 중 하나라도 없는 리포트의 학부모 열람 거부.
- 관리자·조교·졸업생의 개인 일기 접근 거부.
- 여러 역할이 있어도 일기 금지·연령·관계 조건이 무력화되지 않음.
- 미성년·연령 미확인 회원의 성인 전용 활동 접근 거부.
- 클라이언트 변조·직접 API·동시 초대 수락·초대 재사용 검증.
- 비공개 자료가 로그·분석 도구·AI 요청·공개 캐시에 남지 않음.

현재 자동 테스트는 가상 데이터 UI 분리와 계산 로직을 검증한다. 위 서버 보안 항목은 아직 충족되지 않았다.

## 로그인 경로의 적용 범위

`lib/auth/server.ts`는 페이지 요청마다 세션을 확인한다. 실제 연결 모드에서는 Supabase `/user` 확인 후 본인의 활성 계정과 승인 역할 행을 사용자 토큰으로 조회한다. 클라이언트의 역할 선택, URL의 역할, 사용자 메타데이터를 권한 근거로 쓰지 않는다. 회원 홈은 승인된 역할만 제공하고, 본인 프로필 수정 액션도 세션을 재검증한 뒤 본인 ID로만 요청한다. RLS 우회 키는 사용하지 않는다.

개발용 가상 세션은 서명된 별도 HttpOnly 쿠키이며 개발 서버에서만 활성화한다. 누구나 체험 역할을 선택할 수 있으므로 실제 인증으로 취급하지 않는다. 실제 인증 모드와 프로덕션에서는 가상 로그인과 가상 쿠키를 인정하지 않는다. 기존 `/app` 시연의 역할 선택은 여전히 보안 수단이 아니다.

## 졸업생 공동체의 분리 원칙

- 학습 DB의 졸업 상태와 alumni 역할, 별도 승인된 조교·교사 역할은 보존한다. 졸업이 다른 권한을 자동 부여하지 않는다.
- 초기 학습 앱에는 졸업생 게시판·독서모임·친목모임·라운지를 구현하지 않는다. 과거 시연 메뉴는 노출하지 않으며 `/app/community`는 `/mypage`로 이동한다.
- 향후 별도 웹사이트 또는 외부 서비스는 학습 DB와 별도 저장소·접근 정책·보유기간을 갖는다. 졸업 상태를 외부 가입 동의로 사용하지 않는다.
- 공식 홈페이지의 외부 라운지 링크는 운영처 확정, 안전·개인정보 검토, 사용자 승인 후에만 추가한다. 현재는 URL 설정값·가짜 링크·자동 이동을 만들지 않는다.
- 링크를 추가하더라도 식별자·이메일·생년월일·성별·토큰을 URL에 포함하지 않는다. 학습 기록 자동 복사, 외부 계정 자동 생성, 분석 전송, 자동 SSO는 기본적으로 금지한다.
- 향후 선택적 연동이 필요하면 목적별 동의·최소 정보·철회·삭제 절차를 별도 설계한다. 외부 서비스의 관리자 권한이 학습 DB 접근으로 이어지지 않도록 한다.
