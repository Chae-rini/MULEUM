# 운영 모델

> 후속 요청 반영: 생년월일 기반 19세 성년 계산, 기본 계정 5종과 추가 승인 역할, 보호자 다대다 관계, 공식 YouTube 채널 단일 운영을 [회원·공식 영상 설계](MEMBERS_AND_VIDEOS.md)에 구체화했다. 실제 연령 확인·법정대리인 동의·보유기간은 계속 미확정이며 실제 가입은 열지 않았다.

상태: 초기 운영 기준과 후속 설계안. 실제 초대·가입·정산은 미연결이다.

## 정원과 담당 관계

- 승인된 활성 선생님 최대 10명.
- 선생님 한 명당 활성 학생 최대 10명.
- 전체 활성 학생 최대 100명.
- 활성 학생은 기본적으로 주 담당 선생님 한 명을 가진다.
- 추가 선생님의 접근은 별도 승인 관계와 자료 범위를 가진다. 교육팀 소속만으로 모든 학생 자료를 읽을 수 없다.

정원 수치는 운영 기준이지 실제 회원 현황이 아니다. UI에서 숫자를 숨기거나 가입 버튼을 끄는 것만으로 제한을 구현했다고 보지 않는다.

`lib/platform.ts`의 `capacityLimits`와 `capacityIssues`는 동일한 계산 규칙을 서버에서 사용할 수 있게 분리한 순수 함수다. 현재는 테스트 기반 설계이며 초대나 가입을 실제로 통제하지 않는다.

## 서버에서 구현할 정원 검증

1. 초대 발행 시 정원 상황을 확인하고 예상 충돌을 안내한다.
2. 초대 수락·활성화 시 서버에서 유효한 초대, 승인된 담당 선생님, 전체 정원, 담당별 정원을 다시 검사한다.
3. 활성화와 배정, 정원 변경을 하나의 트랜잭션 (Transaction: 전부 성공하거나 전부 취소되는 작업)에서 처리한다.
4. 데이터베이스에서 공통 정원 행과 담당 선생님 행을 정해진 순서로 잠그거나 동등한 직렬화 방식을 적용한다. 동시에 마지막 자리를 수락해도 초과하지 않아야 한다.
5. 주 담당 배정 중복 방지 제약을 둔다. 학생 이전 시 새 담당의 정원을 확인한 후 이전 관계 종료와 새 관계 생성을 함께 처리한다.

권한, 초대의 만료·재사용, 중복 활성화 요청, 동시에 10번째/100번째 자리를 채우는 상황을 테스트한다. 클라이언트가 전달한 정원 수나 승인 여부를 신뢰하지 않는다.

미확정: 휴학·일시중단을 활성 정원에서 제외할 시점, 초대의 자리 예약 여부, 선생님 비활성화 시 이관 절차. 확정 전에는 UI에서 실제 활성화 작업을 제공하지 않는다. 승인된 추가 선생님 관계는 주 담당 정원과 다른 개념이며 집계 정책은 별도 합의한다.

## 초대 기반 가입의 계획

운영 담당자의 권한 확인 → 초대 생성 → 만료 있는 단일 사용 초대 확인 → 필요한 동의·보호 절차 → 계정 생성·역할 승인 → 주 담당 관계 배정 순서를 설계한다. 실제 순서는 보안 설계 시 세분화한다. 공개 가입 폼은 만들지 않는다.

일반 가입, 조교 승인, 선생님 승인, 운영진 승인, 관리자 승인은 서로 다른 절차다. 승인권자 범위, 이중 승인 필요 여부, 해제 절차, 감사 기록 보존 기간은 아직 결정하지 않았다.

## 재학생과 졸업생

회원 계정, 승인 역할 목록, 연령 구분, 재학 상태를 별개로 관리한다.

- 재학 상태: 활성 재학생 / 졸업생 / 해당 없음.
- 연령 구분: 미성년 / 성인 / 미확인.
- 역할: Student, Parent, Teacher, Alumni, Teaching Assistant, Community Operator, Administrator 중 승인된 여러 역할.
- 졸업 처리는 조교·교사·운영진·관리자 역할을 자동 부여하지 않는다.
- 졸업 후 공동체 참여, 모임 참여, 후배 지원은 선택이며 비참여에 불이익을 주지 않는다.

연령 확인 방식, 생년월일 수집 필요성, 연령 재확인 주기와 성인 전환 절차는 개인정보 검토 후 결정한다. 확인되지 않은 나이를 성인으로 추정하지 않는다.

## 공동체와 보호 장치

성인 전용 모임과 미성년자 대상 활동을 명확히 구분한다. 미확인 연령은 성인 전용 영역에 진입시키지 않는다. 졸업 여부만으로 활동 대상 연령을 판단하지 않는다.

성인·미성년자 간 무제한 개인 메시지, 연락처 공개, 사적 매칭을 기본 기능으로 만들지 않는다. 모임 승인·운영자 배정·신고·차단·외부 만남 및 연락 정책을 결정하고 검증하기 전에는 실제 참가와 메시지 기능을 열지 않는다. 보호를 이유로 모든 관리자가 개인 일기를 볼 수 있게 하지 않는다.

## 교육팀 운영

교수법 연구, 회의록, 비식별 교육 사례를 공유한다. 교육팀 공지는 담당 학생 원문과 별도 저장한다. 사례는 이름 제거 외에도 소속·시점·사건 등의 재식별 가능성을 검토해야 한다. 검토 담당과 공개 범위는 후속 결정 사항이다.

## 수익 모델의 설계 범위

학생별 월 과외비에 플랫폼 운영 수수료율을 적용하는 방식을 고려한다. 수수료율, 납부 시점, 환불, 세무, 정산 책임은 미확정이다.

현재 `FeeAgreementDraft`는 월 과외비와 수수료율을 모두 미설정 값으로 표현할 수 있다. 기본 수수료를 임의로 넣지 않는다. 향후 유효 기간이 있는 계약과 월별 원장·조정 내역을 분리해 과거 계산을 재현할 수 있게 검토한다. 실제 결제·정산 API나 수수료 계산·청구 화면은 구현하지 않는다.
